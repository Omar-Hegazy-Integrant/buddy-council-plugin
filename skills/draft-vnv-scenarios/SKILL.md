# Draft V&V Scenarios — Skill

Turn a validated V&V ticket into a set of **high-level scenarios** — the intermediate artifact between a
story and executable test cases. Scenarios say *what must be proven*; test cases say *how*. Stop at the
former: the next stage of the pipeline is a human writing cases in TestRail.

## Where the scenarios live

In the **V&V ticket's description**, under a marked section.

Attachments were the obvious home, but this server has no attachment *upload* tool. `jira_download_attachments`
and `jira_get_issue_images` only read, and although `jira_update_issue` accepts an `attachments` parameter it
expects **file paths on the server's own filesystem** — inside the Docker container, not on the user's
machine — so it cannot upload a locally generated file. The description is the one place that is always
present, always readable by reviewers in Jira, and editable through `jira_update_issue`.

This limit survived the move off Atlassian's official server; do not add a code path that assumes otherwise.

## Input

- `vnv_key`, and its dev source story
- `related_requirements` — from `find-related-requirements`
- `test_cases` — existing cases for that scope, from `fetch-test-cases`
- `platform` — `ios`, `android`, or `both`
- `apply` — when false, render the scenarios and stop

## What makes a good scenario here

Each scenario is one provable behavior, named so a reader knows what it covers without opening it:

- **Cover the requirement, not the implementation.** Anchor each scenario to a requirement ID where one
  exists. A scenario tracing to nothing is a signal — either the requirement set is stale or the story is
  doing something unspecified. Flag it rather than quietly inventing coverage.
- **Include the unhappy paths.** Empty states, permission denials, timeouts, offline, and the boundaries the
  requirements name. These are what the dev story usually omits and what V&V exists to catch.
- **Do not restate existing test cases.** You have them in context. When a scenario is already covered by a
  case, mark it `covered by TC-1234` instead of duplicating it — the value here is the *delta*.
- **Be explicit about platform.** When `platform` is `ios` or `android`, write the scenario for that platform
  and call out anything that differs from the counterpart. When it is `both`, write one set and note the
  per-platform divergences.

## Output format

Replace everything between the markers, preserving all other description content:

```markdown
<!-- bc-vnv:scenarios:start -->
## High-Level Scenarios

_Generated by Buddy-Council `/bc:vnv-sprint-prep` on 2026-08-19. Reviewed by: pending._

### S1 — Sync retries on transient network failure
- **Traces to:** CWA-REQ-85
- **Given** the dashboard is open and the device drops connectivity mid-sync
- **When** the sync request fails with a retryable error
- **Then** it retries up to the bounded limit and surfaces the offline banner
- **Coverage:** new — no existing case
- **Platform notes:** iOS only; Android handles this in the background service (see PROJ-124)

### S2 — Sync gives up after the retry limit
- **Traces to:** CWA-REQ-85
- **Given** every retry has failed
- **When** the limit is reached
- **Then** the user sees a terminal error with a manual retry affordance
- **Coverage:** covered by TC-1234

### S3 — Data is encrypted in transit during retry
- **Traces to:** CWA-REQ-120
- **Given** a retry is in flight
- **Then** the payload uses the same encrypted channel as the initial request
- **Coverage:** new — no existing case

**Not traced to any requirement:** none.
**Open questions:** none.
<!-- bc-vnv:scenarios:end -->
```

Keep `**Not traced to any requirement**` and `**Open questions**` even when empty — their absence is
indistinguishable from an oversight, and a reviewer needs to see that the check ran.

## Writing it to the ticket

1. `jira_get_issue` the V&V ticket and read its current description.
2. **Read-modify-write.** If the markers already exist, replace only what is between them. Otherwise append
   the block. Never overwrite the whole description — the clone's back-reference header lives there.
3. `jira_update_issue` with `issue_key` and `fields` — a JSON **string**, e.g.
   `'{"description": "<the full rewritten description>"}'`. There is no `contentFormat` parameter on this
   server: Markdown is converted unconditionally, so pass the description as plain Markdown.
4. Transition to `jira.vnv_workflow.labels.pending_scenario_validation` (default
   `pending-scenario-validation`) using the remove-then-add procedure in *Label Discipline*
   (`${CLAUDE_PLUGIN_ROOT}/agents/vnv-sprint-prep-agent.agent.md`): strip every pipeline label — including
   the `pending-validation` from cloning and any `pending-questions` from an earlier round — then add this
   one. `src-<DEV-KEY>`, the platform label, and human-added labels are preserved.
5. Stamp `scenarios_written_at` (ISO 8601 UTC) in the progress log.

**Media warning.** Editing a description through this server drops ADF media nodes — embedded images do not
survive the round-trip. Before writing, check the fetched description for media nodes. If any are present,
**do not edit**: report it, print the scenarios in the session so nothing is lost, and let the user paste
them in manually. Silently destroying someone's screenshots is far worse than skipping an automated edit.

## Dry run

With `apply: false`, print the full scenario block exactly as it would be written, plus the label change,
and touch nothing:

```
VV-45 — would write 3 scenarios into the description, add label `pending-scenario-validation`
        (2 new, 1 already covered by TC-1234)
```

## Error Handling

- **No related requirements** → still write scenarios from the story text, but list every one under
  *Not traced to any requirement* and say plainly that traceability could not be established.
- **Description contains media nodes** → skip the edit, print the scenarios, explain why (above).
- **`jira_update_issue` fails** → the ticket is unchanged and keeps its previous label. Report it; do not record
  `scenarios_written_at` for a write that did not land.
- **Ticket already has a scenarios block and is labelled `ready-for-test-case-creation`** → do not overwrite
  approved scenarios. Report that it is already past this stage and leave it alone.
