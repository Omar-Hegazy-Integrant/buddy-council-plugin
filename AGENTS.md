# Buddy-Council Plugin

A plugin for multi-agent requirements/test-case analysis, for Claude Code, Copilot CLI and other AI coding assistants.

## What This Plugin Does

Buddy-Council helps teams detect contradictions, inconsistencies, and alignment gaps between **requirements** (from Jama) and **test cases** (from TestRail). It fetches data live — no RAG, no embeddings, no vector storage.

## Architecture

- **Manifests** — the root `plugin.json` (Agent Plugins 1.0, read by Copilot CLI, VS Code, Codex, and Cursor) and `.claude-plugin/plugin.json` (Claude Code). The root one holds the version. The connectors are declared twice, identically: the root `mcp.json` for Agent Plugins readers and `mcpServers` in `.claude-plugin/plugin.json`; both run `scripts/bc-mcp <name>`
- **Commands** (`skills/<name>/SKILL.md`) — the user-facing entry points (`/bc:contradiction`, `/bc:coverage`, `/bc:ask`, `/bc:setup`, `/bc:onboarding`, `/bc:validate`, `/bc:codemap`, `/bc:vnv-sprint-prep`), each a skill only the user can start, with Codex's picker data in `agents/openai.yaml` beside it
- **Agents** (`com.github.copilot/agents/`) — reasoning engines that orchestrate how-tos to complete tasks; Claude Code's manifest lists each file
- **How-tos** (`howtos/`) — reusable capabilities (fetch data, normalize, analyze, enrich, map to code): plain files a command or agent reads by path
- **Providers** (`providers/`) — one folder per tool (TestRail, Jama, Jira, GitHub): `fetch.md` (how to read it) and `setup.md` (the links it recognizes, its key, how to connect, what setup works out, its recap lines, and its settings). `/bc:setup` reads only the guides a project uses
- **Scripts** (`scripts/`) — `bc_setup.py` (a project's settings: finds the project folder, recognizes links, saves and validates `sources.json`, moves and cleans up older setups' leftovers, forgets a site), `bc_run.py` (run folders, and the onboarding and V&V progress logs), `bc_keys.py` (the key store: one key per site), `bc-mcp` (the launcher every assistant starts the connectors with), `bc_tools.py` (the Plugin Tools, installed from `scripts/automation/`), and `sync_version.py` (the version). `scripts/tests/` holds every script, hook, and manifest test: `python3 -m unittest discover -s scripts/tests`
- **Hooks** (`hooks/`) — the three hook scripts, plus Claude Code's `hooks/hooks.json`; Copilot's hook file is `com.github.copilot/hooks/hooks.json`
- **Connectors** (`mcp-servers/`, ADR 0007, ADR 0008) — the MCP servers the plugin ships and every assistant starts from the plugin's own manifests: `testrail`, `jama`, `atlassian` (the Jira router), and `appium`. **Every tool takes `site`** — the project's `base_url` for that provider — and a connector sends a site's key only to the site it was saved for; a call without `site` uses this computer's only key for that provider, which keeps everyday use outside the commands working. Keys are read on the call that needs them, so a key works the moment it is saved. **The TestRail server both reads and writes**: fourteen `testrail_get_*` read tools — `testrail_get_authoring_defaults` answers setup's whole authoring step in one small result, and three of the others, `testrail_get_requirement_ids`, `testrail_get_linked_cases`, and `testrail_get_canonical_cases` (cases already in the canonical schema, a fraction of the raw size), index the suite by the requirement field (TestRail cannot filter on a custom field) in a 10-minute cache that every write clears — plus `testrail_add_case`, `testrail_add_cases`, `testrail_add_section`, `testrail_update_case`, and `testrail_update_cases`, which create and change cases and folders in the team's live instance. The hook's allowlist globs `testrail_get_*`, so a write tool must never be named `testrail_get_*` — the server's test suite (`mcp-servers/testrail-server/tests/`) fails if one is. **The Jama server is read-only by construction**: eight `jama_get_*` tools, an HTTP client that can only issue GET, and a test suite (`mcp-servers/jama-server/tests/`) that fails if a write path, a non-GET API request, or a tool outside the `jama_get_*` prefix appears — which is what makes the hook's `jama_get_*` glob safe. Never add a Jama write tool, and never swap in Jama's hosted MCP server (Jama Connect MCP via `mcp-remote`): it exposes create/edit/move tools and has no bulk reads. Unlike the TestRail server, it emits the canonical requirement schema itself, because feature scoping needs the whole project tree. Jama answers each request in ~1–1.5 s, so the server reads in parallel (at most 8 requests in flight), reads a project tree in the background — a call that would outlast the client answers `loading: true`, and the same call again joins the read — and reads a list of keys with the batched `jama_get_items`; agents must never loop `jama_get_item` over keys or fan a key list out to sub-agents. GitHub access is handled either via the `gh` CLI or via the assistant's own GitHub connection (the official `github-mcp-server`, not vendored). Jira uses **[`mcp-atlassian`](https://github.com/sooperset/mcp-atlassian)** (`mcp-atlassian@0.23.1`, stdio), which talks to one site per process, so the `atlassian` connector (`mcp-servers/jira-router/`) is a router: it serves mcp-atlassian's 21 `jira_*` tools from a committed schema snapshot (`tools.json`, so they list before any key exists), and hands each call to an mcp-atlassian copy for its site, started through `uv tool run` from that site's key and kept for later calls. **The Jira connector only routes calls to mcp-atlassian, and never talks to Jira itself** — it has no HTTP client, and its tests fail if it imports one. It replaced Atlassian's hosted `mcp.atlassian.com` server in 0.21.1 for two reasons: the hosted one serves **Atlassian Cloud only**, so a Jira Server/Data Center team could never connect, and it then exposed **no board or sprint tools**, which forced every board read to be faked with a project-wide JQL. Its v2 (`/v2/mcp`) has since added board, sprint, and attachment tools, but it is still Cloud-only, and a hosted server cannot be version-pinned — v2 swapped the tool set under existing v1 connections — while the how-tos and the auto-approve hook name `mcp-atlassian`'s `jira_*` tools exactly. **appium-mcp** — the server `/bc:automate` drives the phone with — is not vendored either: `/bc:setup` installs it on each Mac from the lockfile in `scripts/automation/appium-mcp/`, on bc's own pinned Node, and the `appium` connector starts it (`bc_tools.py serve`) — or answers with no tools until it is installed.
- **Config** (`config/`) — source selection and non-secret configuration

## Data Flow

```
Command → Agent → How-tos (fetch → normalize → analyze) → Human-readable report
```

Requirements and test cases are fetched live from configured sources, normalized to a canonical schema, linked by ID references, then analyzed by the assistant's model.

## Key Conventions

- All commands use the `bc:` prefix
- **README stays current**: any change that alters user-visible behavior — commands, the setup flow, the config schema, prerequisites, permissions, install or release steps — must update `README.md` in the same change set. A stale README is part of the bug, not a follow-up.
- **Commands are the only skills, and only the user starts them** (ADR 0006). Each `skills/<command>/SKILL.md` carries `name` (its folder's name), a one-line human-facing `description`, and `disable-model-invocation: true`, which keeps its description out of every session's context; its `agents/openai.yaml` sets `policy.allow_implicit_invocation: false` for Codex. Everything internal is a **how-to**: a plain Markdown file in `howtos/`, with no frontmatter, reached only through a command's or agent's instructions. Assistants load every skill they find under `skills/`, so a how-to never goes there. `scripts/tests/test_manifests.py` fails on a skill without these fields, a how-to under `skills/`, or a how-to nothing names.
- **Paths are relative to the plugin root.** A command skill's base directory is `<plugin root>/skills/<name>/`, so the plugin root is two folders up — every command says so near its top — and every file is named by its path from there: `howtos/<name>.md`, `providers/<name>/fetch.md`, `scripts/bc_run.py`, `com.github.copilot/agents/<name>.agent.md`. `${CLAUDE_PLUGIN_ROOT}` and `$ARGUMENTS` are substituted only by Claude Code, so instruction files use neither: a command reads "the text the user typed after the command". An agent started on its own gets no base directory, so its caller passes `plugin_root` in the prompt. The manifest tests check that every path an instruction file, `AGENTS.md`, or `README.md` names exists.
- **Two manifests, one version** (ADR 0007). The root `plugin.json` is the only place the version is set; `python3 scripts/sync_version.py` copies it into `.claude-plugin/plugin.json`, and `--check` (run by the manifest tests) fails while they differ. `marketplace.json` carries no version. The root manifest takes only Agent Plugins fields — no component paths: Copilot CLI and VS Code read agents from `com.github.copilot/agents/` and hooks from `com.github.copilot/hooks/hooks.json`, fixed locations in that format, while Claude Code's manifest lists each agent file under `agents` (it accepts files, not folders; `claude plugin details` counts none of them, but they load — `--debug` shows each). The connectors are declared in the plugin itself — the root `mcp.json` for Agent Plugins readers and `mcpServers` in `.claude-plugin/plugin.json` for Claude Code, kept identical (see *Connectors are declared in two manifests* below). `claude plugin validate . --strict` must pass.
- No hardcoded secrets — **keys belong to sites** (ADR 0008): one file per site in `~/.buddy-council/keys/<site>.json`, mode 600 in a 700 folder, holding the provider, the URL it was saved for, and the credential — `username` + `api_key` (TestRail), `client_id` + `client_secret` or `username` + `password` (Jama), `username` + `api_token` or `personal_token` (Jira). A site is the URL's host, a non-default port, and any path prefix. `scripts/bc_keys.py` is the only code that reads or writes them; the connectors import it by path. A connector talks only to the URL saved in the key it uses and follows no redirect, so a key never reaches another site; no connector reads a credential from an environment variable, and no assistant setting carries one. Setup writes a key with the file tool (never on a command line), after `bc_keys.py path` says where, and `bc_keys.py check` makes it private; neither prints a key. One key per site; `check` names who a key signs in as (`user`, never the secret half). A `github` key — a read-only token, the last resort for design documents — belongs to its host the same way. **Migration:** older setups kept TestRail and Jama (and a github.com token) in `~/.buddy-council/secrets.json` — TestRail once in `~/.buddy-council-secrets.json` — and Jira in `~/.buddy-council/atlassian.env`; `migrate_legacy()` copies the TestRail, Jama, and Jira keys to the site recorded beside each (the secrets' `base_url`, the `*_BASE_URL` of bc's own old connector entries — in `~/.copilot/mcp-config.json` and every bc plugin folder's `.mcp.json`, counted as bc's only when the folder they run from has a manifest naming `bc`, never by its name alone — or `JIRA_URL`), never guesses a site (settings that disagree leave the key where it is), never replaces a saved key, runs once per computer, and leaves the old files in place. The connectors run it on their first call, so everyday use survives the update day. `/bc:setup` runs it through `bc_setup.py migrate`, checks each migrated site through its connector, then `bc_setup.py cleanup --verified <sites>` removes what older setups left — the migrated sections of `secrets.json`, `atlassian.env`, and bc's own `testrail`, `jama`, `atlassian`, `github`, and `appium` entries in `~/.copilot/mcp-config.json` and bc's plugin folders' `.mcp.json` (only entries that run bc's servers, bc's env file, bc's token, or bc's tools folder) — for the sites that answered, and only under the current home folder. Files bc didn't create (`atlassian.env.server-dc.bak`) are left alone and named once. The GitHub token is never moved by `migrate_legacy()`: a token is saved only as a last resort, so `bc_setup.py github --move-old-token yes` makes it the github.com key only when nothing else reads the project's documents (`providers/github/setup.md`); until then it stays in `secrets.json`, and cleanup says so once. bc's `github` entry goes on the first cleanup either way, because no token stays in connector settings. `bc_keys.py` is the only code that reads the old files too: `legacy_sections()` and `legacy_jira_url()` name sites, never keys.
- **The connectors ship inside the plugin, so setup writes no connector settings** (ADR 0007). The server names stay `testrail`, `jama`, `atlassian`, and `appium`, and the tool names stay as they were, because Copilot gives a plugin's MCP server precedence over a same-named one in `~/.copilot/mcp-config.json` — the plugin's connectors replace the ones older setups registered there, and everyday `jira_*` calls keep working. `/bc:setup` never writes `.mcp.json` or `~/.copilot/mcp-config.json` again; it only removes bc's own old entries from them.
- **Connectors are declared in two manifests, started by one launcher**: the root `mcp.json` (Agent Plugins `$schema`, closed envelope, `"type": "stdio"`, `"command": "sh"`, `"args": ["./scripts/bc-mcp", "<name>"]` — relying on the plugin root being the default `cwd`, because `command` is never placeholder-expanded and Cursor doesn't expand `${PLUGIN_ROOT}`) and `mcpServers` in `.claude-plugin/plugin.json` (`"${CLAUDE_PLUGIN_ROOT}/scripts/bc-mcp"`). `scripts/tests/test_bc_mcp.py` keeps the two identical. `scripts/bc-mcp` is POSIX `sh`: it finds the plugin root (`PLUGIN_ROOT`, `CLAUDE_PLUGIN_ROOT`, `CURSOR_PLUGIN_ROOT` when it holds the launcher, else its own path), finds `uv` on `PATH` or in `~/.local/bin`, `/opt/homebrew/bin`, `/usr/local/bin`, `~/.cargo/bin` — an assistant opened from the Dock has none of those on `PATH` — and `exec`s the server (`uv run --frozen` in its folder). It prints nothing on stdout, the MCP stream; no `uv` is one line on stderr. In Claude Code the plugin's tools are named `mcp__plugin_bc_<server>__<tool>`; Copilot CLI names them `<server>-<tool>` in its hook payload; `hooks/auto-approve-mcp.sh` and `settings.json` match every spelling, old names included.
- **Settings belong to a project folder** (ADR 0008): `.buddy-council/sources.json` in the nearest folder at or above the current one that holds `.buddy-council/` — never the key store's own `~/.buddy-council`. Every command starts with `howtos/load-settings.md` (`bc_setup.py status --from … --need … --reads …`: the folder the session started in — Copilot's shell keeps a `cd` between calls — the tools it can't run without, and the ones it reads when the project has them), which finds it and says what to stop on, ask for on the spot, or print — a key is asked for only by a command that reads that tool. The same how-to holds the rules for the whole command: a plugin script runs as one plain command, never after a `cd` or in a chain; files are read with the view or grep tool, never parsed in the shell; and a tool's answer stays small enough to show at once — Copilot moves anything over about 20 KB into a file outside the project, which costs a permission prompt to read. Settings name no plugin path (`plugin_root` is gone) and stay git-excluded through the clone's `info/exclude`. **`scripts/bc_setup.py` is the only code that saves them** — setup, `/bc:vnv-sprint-prep`'s V&V board, the platform field id `check-platform-parity` caches, and `bc_tools.py`'s `automation` block (through `bc_setup.save`) — and it refuses a save holding anything `config/sources.example.json` lacks. The example lists every setting the plugin reads (a `"*"` key stands for any key), and the tests fail when it doesn't, or when a guide's ```` ```json settings ```` block wouldn't validate. **Only requirements are required** (ADR 0009): `test_cases` and `jira` take `{"provider": "none"}`, saved on purpose; any tool can be `"pending": true` (not verified), retried by the next `/bc:setup`. Analysis stops while requirements or test cases are unverified and skips an unverified board; every report prints one line for a tool the project doesn't use (`Board: not used in this project. Add it with /bc:setup <board link>.`).
- **Scripts save, so nothing prompts, and no hook approves a file write.** The old write hook (`auto-approve-plugin-writes.sh`) is gone: settings are saved by `bc_setup.py save` and the onboarding and V&V progress by `bc_run.py progress` (plus `note` and `archive`), which `validate-bash.sh` approves as one plain command. Structured data travels as **one single-quoted JSON argument on one line, with every `'` written as `\u0027`** — never a pipe, heredoc, or redirect, which the hook can't approve. A patch merges: objects key by key, anything else replaces, `--unset` removes a setting first; a progress log's own list merges item by item (`features` by `name`, `stories` by `dev_key`). A key the assistant writes with its file tool always reaches the assistant's prompt, and that prompt is the approval.
- **Setup asks by link** (`skills/setup/SKILL.md`, about 10 KB, and the provider guides): one message for the links (Jama project, TestRail suite, Jira board — "none" for the last two), keys only for sites with no key on this computer (`bc_setup.py links` says which, worded per site), and on a computer with no keys, links and keys in one message. Everything else is derived and shown in one recap, then "Save?". A change is one link or sentence (`/bc:setup <link>`, `/bc:setup no Jira`, `/bc:setup forget <site>`), recapped `before → after`; a bare re-run re-checks every site and setting and asks nothing when nothing changed. Other files name a guide, never a setup step number (a test fails otherwise).
- Provider guides are swappable — adding a new provider means adding a `providers/<name>/` folder, plus its links and key fields in `scripts/bc_setup.py` and `scripts/bc_keys.py` and its settings in `config/sources.example.json`
- Agents never call providers directly — they go through router how-tos (`fetch-requirements`, `fetch-test-cases`, `fetch-board-issues`)
- **Data Contract**: every analysis command fetches **every configured source** — requirements and test cases always, plus GitHub doc enrichment whenever a Jama `github_url` field is mapped and `requirements.enrichment.enabled` is true, plus **Jira board issues** whenever the board is ready (scope narrows a fetch, never skips one). A board the project doesn't use, or one not verified yet, is *skipped with its line from `bc_setup.py status`, not failed* — it does not make the run PARTIAL; a ready board that errors does. Each attempt is surfaced as a visible `Fetch:`/`Readiness:`/`Enrichment:` line, and if any configured source fails the agent stops and asks the user whether to continue with partial data — continuing marks the output **PARTIAL**. Tool calls are logged to `.buddy-council/logs/` by a bundled PostToolUse hook in Claude Code, Copilot CLI, and VS Code.
- **Mechanical work runs on a low-cost model, and the data moves as files.** `/bc:coverage` and `/bc:contradiction` collect through `howtos/collect-artifacts.md`: the hidden `bc:data-collector` sub-agent fetches requirements (`jama_get_requirements` with `save_to`), every test case in the suite (`testrail_get_canonical_cases` with `save_to`), and the GitHub docs (`bc_run.py enrich`, gh CLI strategy) into a **run folder**, `<project>/.buddy-council/runs/<run-id>/`, and `bc_run.py link` cross-links them in code — counts, untested, orphans, stranded links, per-feature Markdown **bundles** of at most 18 KB a part. The main model reads the run through `bc_run.py summary` — the checks, the lines, the counts, and the feature rows in a few KB, then `--feature` for one feature's bundle-part paths and lists; `links.json` itself is for code, and a whole project's runs to about 100 KB — then one feature's bundle parts — custom fields included (Jama platform/product/version/trace fields; TestRail fields by label with dropdown and multi-select ids resolved to option names) — plus the docs the feature links to, split into parts of the same size; it never recounts what the code counted, and no model retypes requirement or test case text. **The collector's word is never trusted**: `link` checks the run against `sources.json` (the Jama file records the site and the arguments it was read with; TestRail's records site, suite, requirement field, and filter — two sites can both have a project 42) and writes the `Fetch:`/`Enrichment:`/`Readiness:` lines itself, so a wrong argument becomes a listed mismatch — and the caller re-collects inline once — instead of a quietly wrong report. Feature runs find unlinked cases in folders that contain the feature's name as whole words. **One agent file serves every assistant**: its `model` frontmatter is the list `[claude-haiku-4.5, gpt-5-mini]`, which Copilot CLI (1.0.83+) tries in order and Claude Code ignores because it only parses a string, so the caller passes `model: "haiku"` per call under Claude Code and no model elsewhere. Its `tools` list names each tool in both Claude Code's and Copilot's spellings — each ignores the names it does not know. If the sub-agent cannot run — or the assistant has none, as Codex and Cursor don't load plugin agents — the caller follows the same steps inline. **`save_to` is the servers' only local side effect**: it writes one JSON file into an existing run folder, refuses any other path or a symlink, and never creates a directory — `bc_run.py new` does, keeping the newest 5 runs for at most a week. Setup uses the same hand-off: `testrail_get_requirement_ids` saves every linked ID into a setup run folder (`bc_run.py new --command setup`, the one run that may create `.buddy-council/`), and `jama_get_scope_proposal` reads them back with `document_keys_file`, validated the same way, so no ID list passes through the conversation. `hooks/validate-bash.sh` approves `bc_run.py` only as one plain command — `python3`, this plugin's own copy by absolute path, a known subcommand and options, arguments bare or single-quoted. The script is stdlib-only and must keep running on macOS's Python 3.9. `/bc:ask` lookups use the same run folders: `bc_run.py recent` reuses a complete run of the whole scope up to 30 minutes old after re-checking it against `sources.json`, and `bc_run.py search` writes the ranked results to `search/` in the run. **On Jama, a lookup run also holds `background.json`** — the rest of the project: every item outside the requirements in scope, minus excluded item types and subtrees, written by the same `jama_get_requirements` call as the requirements (`background_save_to`), so the two can never be read with different arguments; `bc_run.py new` hands out a background path only for a lookup, and `link` ignores a background file in any other run. `search` ranks it apart, as an *Elsewhere in the project* section, and no count, bundle, or report ever includes it; `link` treats a Jama lookup without it as a missing source, and `recent` never reuses a Jama run that lacks it. Board issues, and docs under the `mcp` enrichment strategy, are still fetched by the main model.
- **`/bc:vnv-sprint-prep` writes to other teams' tickets, so it is dry-run by default.** A plain run performs zero `jira_create_issue`/`jira_add_comment`/`jira_update_issue`/`jira_create_issue_link`/`jira_add_issues_to_sprint`/`testrail_add_cases`/`testrail_add_section`/`testrail_update_cases` calls and prints a plan; `--apply` executes after one batch confirmation *per phase*. Never widen this: the auto-approve hook deliberately excludes every Jira write tool, and no `--allow-tool` recipe may list them.
- **One TestRail writer.** Every path that creates test cases — `/bc:vnv-sprint-prep` phase 7, the `/bc:coverage` gap-fill offer, and `/bc:ask` scenario mapping (`scenario-mapping-agent`) — goes through `howtos/draft-test-cases.md`. Callers trace and duplicate-check; the how-to writes. Never add a path that calls `testrail_add_*` directly: writing the requirement field is what makes a created case count as coverage, and a second writer is how it gets forgotten.
- **One TestRail updater.** Every path that changes an existing case — `/bc:ask` edits, the `/bc:coverage` orphan repair, the `/bc:contradiction` fix offer, and phase 7's refresh of revised V&V scenarios — goes through `howtos/update-test-cases.md`. Never call `testrail_update_*` directly. The how-to reads each case fresh, plans a before → after diff, applies it with the conflict guard, and passes `requirement_field` on every call so the server refuses to drop a requirement link the user did not ask to remove. **An update never overwrites human work**: phase 7 only regenerates a V&V skeleton whose TestRail `updated_on` still matches what the plugin recorded when it wrote it (`testrail_cases[].written_on`), and reports any case the V&V team has edited instead.
- **V&V scenarios live in the ticket description, not an attached `.md`** — `mcp-atlassian` can upload files (`jira_update_issue` takes local paths in `attachments`), but the description is always present, readable by reviewers in Jira, and editable through `jira_update_issue`. `mcp-atlassian` also creates issue links (`jira_create_issue_link`), so clones get a real Jira link *and* keep the `src-<DEV-KEY>` label: the label is what the duplicate guard searches on, since one board query beats a link traversal per issue. A site that refuses link creation degrades to label-only rather than failing the clone.
- **The Plugin Tools are bc's own, pinned, and set up without a question.** `/bc:setup` runs `scripts/bc_tools.py` only when the project is an Appium or WebdriverIO test project with a phone app — analysis-only users download nothing — and its plan rides on the recap's one "Save?" ("leave out automation" skips it). It installs Node (by version and SHA-256, `scripts/automation/pins.json`) and appium-mcp (by the shipped `scripts/automation/appium-mcp/package-lock.json`, `npm ci --ignore-scripts`) into `~/.buddy-council/tools`: **never on PATH, never shared**, and nothing ever edits a shell profile, `JAVA_HOME`, or `ANDROID_HOME`, or replaces a working tool the Mac has — a missing JDK or Android SDK goes beside it, only for Android on the built-in drivers and only after the recap named it. The script itself writes the record the plugin's `appium` connector starts appium-mcp from (`~/.buddy-council/tools/appium-mcp.json`: absolute paths, `NO_UI=true`, `REMOTE_SERVER_URL_ALLOW_REGEX` limited to this Mac, `ALLOW_REMOTE_APP_URLS=false`) and the `automation` block in `sources.json`, after proving the server answers (`ensure`) and reading one page source from the phone (`smoke`, a second call so each fits Claude Code's 10-minute shell limit); no phone means `pending`, re-checked by the next `/bc:setup` like a pending Jira board, and a passed check is kept as `proof` so an unplugged phone doesn't undo it. No assistant's settings are ever written; until the first install, the `appium` connector answers with no tools (`bc_tools.py serve` runs a stdlib stub), and after it the assistant needs one restart to load appium-mcp's tools. The project's own Appium server is used when the Mac has it with the drivers the tests need (through appium-mcp's `remoteServerUrl`), appium-mcp's built-in drivers otherwise. The project's own setup script runs only through `bc_tools.py project` (check before the recap, fix after the save), and what still needs a person — `sudo`, the App Store, signing, the phone — is passed on, never attempted. A pin changes only in a plugin release whose device check passed; the next `/bc:setup` installs it, keeps the old version in use until the new server answers, then prunes it. Downloads use the Mac's proxy, `~/.npmrc`, keychain certificates, and `NODEJS_ORG_MIRROR`; a failed one is `pending` and retried. `hooks/validate-bash.sh` approves `bc_tools.py` like `bc_run.py` **except** `project` (it runs the project's code) and `remove`, which always prompt; `hooks/auto-approve-mcp.sh` approves only appium-mcp's eight read-only tools plus page sources and screenshots — in every spelling, including Claude Code's `mcp__plugin_bc_appium__<tool>` and Copilot's `appium-<tool>` — and `READ_TOOLS` in the script must match it (its tests fail otherwise). The script is stdlib-only and must keep running on macOS's Python 3.9; it deletes and stops things itself, because the bash hook blocks `rm -r` and `kill`.
- **Hooks are dual-manifest**: `hooks/hooks.json` (Claude Code format) and `com.github.copilot/hooks/hooks.json` (Copilot format, `version: 1`, read by Copilot CLI and VS Code) register the same three scripts — Copilot reads only the latter once the root `plugin.json` exists, so neither fires twice. Codex and Cursor run without hooks for now. The scripts are runtime-agnostic — they parse both payload shapes (`tool_name`/`tool_input` object vs `toolName`/`toolArgs` JSON-string) and emit both decision shapes (top-level `permissionDecision` for Copilot, `hookSpecificOutput` wrapper for Claude Code). Keep all of that intact when editing a hook, and never let a preToolUse script exit non-zero incidentally — Copilot treats that as deny (fail-closed). Claude's hook commands keep `"${CLAUDE_PLUGIN_ROOT}"` in double quotes, which `claude plugin validate --strict` requires. Copilot runs hook commands with cwd = the plugin dir and `PLUGIN_ROOT` set to it, so project paths must come from `CLAUDE_PROJECT_DIR`/`COPILOT_PROJECT_DIR` or the payload's `cwd`, never the process cwd.

## Available Commands

- `/bc:setup` — Connect a project folder to its tools from their links: the Jama project (required), the TestRail suite, and the Jira dev board ("none" for either), with keys asked only for sites new to this computer. Everything else is worked out and shown in one recap, then "Save?": Jira Cloud or Server, project, suite, board, field mapping (from `jama_get_item_types`' `field_candidates`), item types, the Jama scope anchored on what the TestRail suite links to — the whole document (Jama set) holding them as the root, the folders they sit in as features, the rest of the project as background — test-case defaults, how GitHub docs get read, and code mapping. In an Appium or WebdriverIO test project it also installs and proves the Plugin Tools with no extra question. One run finishes, with no restart — except once after it installs or updates the Plugin Tools (ADR 0002). A bare re-run re-checks everything and asks only about what broke; `/bc:setup <link>` or `/bc:setup <sentence>` changes only that part; `/bc:setup forget <site>` deletes a key. Updating from 0.27.0 is one run that asks nothing when everything still connects.
- `/bc:contradiction` — Detect contradictions between requirements and test cases, one feature's run-folder bundle at a time. Each requirement-vs-test finding names the side to fix; when that is the test case, the report ends with an offer to update those cases through `update-test-cases`
- `/bc:coverage` — Find untested requirements, orphan test cases, and coverage gaps. Collects into a run folder through the low-cost `data-collector`; the counts come from code. Ends with up to two offers, repair first: re-link orphan cases (a requirement ID stranded in References is copied into the requirement field; unlinked cases get suggested links the user confirms), then draft cases for requirements that are genuinely untested
- `/bc:ask` — Natural language query — routes to the right agent or answers directly. When the user describes a behavior in their own words and asks whether or where it is specified, routes to `lookup-requirements`: the model words the ask as concepts with alternative wordings, `bc_run.py search` ranks every requirement in scope against them in code (BM25, no embeddings) — on Jama, the rest of the project too, as background that enriches the answer but never covers the ask — and the model judges the top 25 — covers, partly covers, conflicts, related — searching again before it ever answers "not specified". When the user brings their own high-level scenarios (a file, pasted text, or a Jira key), routes to `scenario-mapping-agent`, which traces each scenario to requirements, checks it against existing cases, confirms the mapping, and writes the cases through `draft-test-cases`. When the user asks to change cases they name (`update C1234 …`, `add CWA-REQ-90 to TC-55`), routes to `update-test-cases`' edits path
- `/bc:onboarding` — Walk a new team member through the product feature-by-feature with paced demos, do/don't pairs from test cases, optional code mapping when run from inside a codebase, and an assessment phase. Progress is logged to `.buddy-council/onboarding-progress.json` in the user's project root and resumes across sessions.
- `/bc:validate` — Validate Jira tickets against requirements and test cases (gap and contradiction detection)
- `/bc:codemap "<feature>"` — Map a single feature to where it lives in the current codebase (files, communication flow, per-requirement locations). Same output as the onboarding code-mapping phase, invokable standalone.
- `/bc:vnv-sprint-prep` — Run the V&V (Validation & Verification) sprint workflow: check cross-platform parity on the dev board, clone sprint stories onto the V&V board, validate them against requirements and test cases, draft high-level scenarios, drive label state through review, and write the approved scenarios into TestRail as skeleton test cases (phase 7) — refreshing them when approved scenarios are later revised, by re-review or by a hand edit of the approved ticket, without ever overwriting a case the V&V team edited. It asks only for its V&V board's link, the first time; what puts an issue on that board is derived by comparing the two boards, the reviewer is whoever runs it, and both show in its plan, where the user can change them. Dry-run by default; `--apply` writes. Resumable — re-run it to pick up dev answers and reviewer approvals.

## Canonical Artifact Schema

All providers normalize data to this shape before analysis:

```json
{
  "type": "requirement | test_case | board_issue | background",
  "id": "CWA-REQ-85",
  "title": "...",
  "description": "...",
  "rationale": "...",
  "feature": "Feature Name",
  "status": "Active",
  "linked_ids": ["TC-1234"],
  "raw_fields": {},
  "extended_context": [
    {
      "source": "github",
      "url": "https://github.com/org/repo/blob/main/docs/sds.md",
      "locator": { "owner": "org", "repo": "repo", "path": "docs/sds.md", "ref": "main", "anchor": null },
      "content": "<markdown verbatim>",
      "fetched_at": "ISO 8601 UTC",
      "referenced_images": [{ "alt": "...", "url": "https://raw.githubusercontent.com/..." }],
      "truncated": false
    }
  ]
}
```

The `extended_context` field is **optional** — populated only when:
- The provider extracted a `_enrichment_urls` transient field from the source (e.g., the Jama field mapping names a `github_url` field), AND
- `requirements.enrichment.enabled === true` in `.buddy-council/sources.json`, AND
- The fetch succeeded.

Every downstream how-to treats it as optional and reads `description` non-exclusively, so legacy data and disabled-enrichment paths work unchanged.

## Configuration Schema Additions

`.buddy-council/sources.json` supports these additional blocks for richer onboarding and analysis:

- **`requirements.feature_inference`** — `{strategy: "hierarchical_folder", folder_item_type: "Folder", depth}`. Controls how requirements are grouped into features. `/bc:setup` always writes `hierarchical_folder` without asking. For Jama with `requirements.roots`, `depth` (default 1) makes a requirement's feature the container that many levels below its root — the root's top-level folders by default, deeper folders rolled up — instead of its nearest folder. `/bc:setup` sets it so the features are the folders the test-linked requirements sit in, however deep inside the root's document they are. For Jama, `folder_item_type` is the item type that marks a feature — Jama **folders** by default — and the server reads the real tree: a requirement's feature is its nearest folder (else its Set/Component), and a feature scope covers the whole folder subtree.
- **`requirements.item_type_filter`** — array of `Item Type` values to include (everything else is ignored). Setup's scope step (`providers/jama/setup.md`) writes it with the item type(s) the test suite's requirement links point to; values match item-type display names or type keys.
- **`requirements.item_type_exclude`** — array of `Item Type` values to skip even when they carry IDs (e.g. `["Text"]` narrative items). Written automatically by `/bc:setup` when the Jama project holds `Text` or test-case items (`Test Case`), since test cases come from TestRail; hand-editable for other types. Jama Folders, Sets, and Components are never requirements, with or without this list.
- **`requirements` for Jama** — `{provider: "jama", base_url, project_id, project_key, project_name, field_mapping, roots, exclude}` alongside the shared `feature_inference`, `item_type_exclude`/`item_type_filter`, and `enrichment` blocks. `base_url` is the Jama root — the `site` every Jama call passes; `project_id` is an integer. **`field_mapping`** maps `{status, rationale, github_url}` to Jama field **labels** (defaults: `status` → `"status"`, `rationale` → `"rationale"`, no GitHub field). `id`, `title`, and `description` are fixed — the document key, Name, and Description. A `github_url` field feeds `_enrichment_urls`. No credentials ever appear in this block. **`roots`** (`[{id, path}]`) are the requirements roots setup's scope step anchors on the requirement IDs the TestRail suite links to (`jama_get_scope_proposal`) — the whole document (Jama set) holding them, chosen without a question. Only what sits inside them is in scope for every command, so a large project's other documents and archives never reach a report — `/bc:ask` lookups search them as background (`background.json`), never counted. **`exclude`** (same shape) leaves subtrees inside a root out — an archive the user named. The `id` is what the server uses; the `path` is for people. Without `roots`, the whole project is in scope and every folder is a feature; a configured root that no longer exists is reported, never silently widened.
- **`requirements.enrichment`** — `{enabled: bool, strategy: "cli" | "mcp", max_doc_chars: int, check_url}`. Drives GitHub-doc enrichment when a `github_url` field is mapped. `cli` means the plugin reads the documents itself with the first sign-in that works (`gh`, then `GH_TOKEN`/`GITHUB_TOKEN` for github.com — for a GitHub Enterprise host, only the one named in `GH_HOST`, with `GH_ENTERPRISE_TOKEN`/`GITHUB_ENTERPRISE_TOKEN` — then the host's saved `github` key, then none for public repositories); a token in the environment never goes to a host the user didn't name, and `gh` runs without it there. `mcp` means the assistant's own GitHub connection. `check_url` is the document setup last read, so a re-check reads the same one (`providers/github/setup.md`).
- **`test_cases.authoring`** — `{template_id, type_id, priority_id, requirement_field, section_strategy, section_root, create_missing_sections}`. What `/bc:vnv-sprint-prep` phase 7, `/bc:coverage`'s gap-fill offer, and `/bc:ask`'s scenario mapping need in order to *create* cases, as opposed to read them. **`requirement_field`** (default `custom_jama_req_id`) is the custom field this plugin reads to build a test case's `linked_ids` — every created case must populate it **and** the built-in `refs`. It holds plain IDs separated by a comma and a space (`CWA-REQ-85, CWA-REQ-86`), the only form traceability tools read: given `requirement_field`, the create and update tools write it that way and refuse a value that isn't a requirement ID, so every call that writes the field passes it. Writing only `refs` is a silent failure: the case looks right in TestRail but comes back an orphan, leaving its requirement untested and making the next coverage report worse. Resolved once by setup (`providers/testrail/setup.md` → *Authoring*) against the live instance, because TestRail takes **ids, not names**, and they differ per instance. `template_id` is the one that bites: it decides which body fields a case has, so a steps-style template is required for `custom_steps_separated` to hold Given/When/Then. `section_strategy` is `"linked"` (beside the existing cases for the same requirement, else for the same feature — found with `testrail_get_linked_cases` — else a feature folder), `"feature"` (folder path from each requirement's feature), or `"fixed"` (everything under `section_root`); `section_root` may be `null`. **Phase 7 skips itself with a visible line when this block is absent** — it must never guess a template.
- **`jira`** — `{provider: "jira" | "none", base_url, deployment, project_key, default_issue_type, board: {url, id}, pending}`. Optional (ADR 0009): `{"provider": "none"}` records a project that uses no Jira, and an older block without `provider` is Jira. `deployment` is `"cloud"` or `"server"`, detected from the host (`*.atlassian.net` → cloud), and decides the auth style. `board.url` is the dev board URL the user pasted and `board.id` the integer parsed out of it; `project_key` comes from that URL, or is derived from the board's first issue when a classic RapidBoard URL omits it. `pending: true` means the connection test failed — `/bc:setup` re-tests and clears it on the next run, analysis commands skip the board source while it is set, and `/bc:validate` and `/bc:vnv-sprint-prep` stop. `requirements` and `test_cases` take `pending` the same way, and analysis stops while either is set. **There is no `cloud_id`**: every Jira call passes `site` — `base_url` — and the connector hands it to an mcp-atlassian copy bound to that site. The credential is the site's key in `~/.buddy-council/keys/`, never here.
- **`jira.vnv_board`** — `{url, id, project_key, discriminator}`. The V&V team's board, saved by `/bc:vnv-sprint-prep` from the one link it asks for (setup never asks for it), following `providers/jira/setup.md` → *The V&V board*. **It may share a project with the dev board** — one project with two boards is a normal Jira layout, and everything here is addressed by board id. Only a duplicate board **id** is refused. When the projects match, `discriminator` (`{kind: "label"|"component"|"issue_type"|"sprint", value, confidence, sampled_at}`) records what the V&V board's filter keys off, so clones land on it; it is `null` when the V&V board has its own project. It is derived by sampling both boards, shown in the dry-run plan, and asked for only when the samples settle nothing.
- **`jira.platform`** — `{field_name, field_id, values, require_parity, title_prefix_fallback}`. Drives the cross-platform parity check. `field_name` defaults to `OS`; `field_id` is the resolved custom-field id, cached after first discovery and re-discovered when stale. The title prefix is a fallback only, and any result derived from it is reported as lower-confidence.
- **`jira.vnv_workflow`** — `{reviewer: {account_id, display_name}, approval_phrases, labels}`. Who may approve scenarios — `reviewer` only when the user named someone; without it, whoever runs `/bc:vnv-sprint-prep` and what the **four** pipeline labels are called: `pending_validation` (set at clone) → `pending_questions` → `pending_scenario_validation` → `ready_for_test_cases`. **They are mutually exclusive** — every transition removes the previous pipeline label rather than stacking, while preserving `src-<DEV-KEY>`, the platform label, and anything a human added. A ticket with no pipeline label is treated as `pending_validation`; one with several is repaired to the furthest-along and the repair is reported. `/bc:vnv-sprint-prep` writes the defaults without asking; hand-edit to rename labels.
- **`project`** — `{enabled: bool, ignore_dirs: [string], id_patterns: [regex]}`. Controls code mapping for `/bc:onboarding` and `/bc:codemap`. When `enabled` is true and cwd contains code markers, the onboarding agent runs a code-mapping phase between demo and assessment for each feature.
- **`automation`** — written only by `bc_tools.py ensure`, never by hand: `{enabled, status: "ready" | "pending", pending: [reasons], guided: [what only a person can do], stack, platforms, driver: {mode: "project" | "built-in", appium, version, drivers}, phone, apps, language, setup_script, tools: {node, appium_mcp, jdk?, android_sdk?}, server, proof: {phone, udid, platform, mode, page_source, bytes, checked_at} | null, checked_at}`. `{"enabled": false}` records "leave out automation", and setup then never brings it up by itself. Setup's re-check reads the block through `bc_tools.py status`; `bc_tools.py` saves it through `bc_setup.save`, which checks it against the example; `/bc:automate` will read the driver, phone, app, and stack from it.
- **`version`** — the settings format, `2` since 0.28.0, stamped by `bc_setup.py save`. Settings without it were saved by an older setup: every command stops with "run /bc:setup once to finish updating", and that run's save drops `plugin_root` (commands find the plugin root from their own skill folder; an agent run on its own gets it in its prompt) and `jira.cloud_id`, and fills `jira.deployment` from the host.

## V&V Progress Log

`<project>/.buddy-council/vnv-progress.json`, saved by `/bc:vnv-sprint-prep` through `bc_run.py progress` (stories merge by `dev_key`). One entry per sprint story:
`{version: 1, sprint, dev_board_id, vnv_board_id, started_at, updated_at, stories: [{dev_key, vnv_key,
platform, platform_source, counterpart, parity, state, concerns, concern_comment_id, concern_posted_at,
scenarios_written_at, scenarios_source, scenarios, testrail_case_ids, testrail_cases, cases_created_at,
cases_updated_at, approved_by, approved_at, last_checked_at}]}`. Timestamps are ISO 8601 UTC.

`scenarios` is phase 5's structured output (`{id, title, traces_to, given, when, then, coverage, covered_by,
platform_notes}`), cached here because a Jira description is a **lossy** carrier — `jira_update_issue`
converts markdown to wiki markup on Server/DC, so what phase 5 wrote is not what a later read returns.
Phase 7 reads it from here rather than re-parsing prose. `testrail_case_ids` and `cases_created_at` record
what phase 7 wrote, and are only a secondary guard: phase 7 asks **TestRail** first, via
`testrail_get_cases_by_refs` on the dev key. `testrail_cases` (`{scenario, case_id, written_on}`) maps each
scenario to its case, where `written_on` is the case's TestRail `updated_on` as the plugin last wrote it — a
refresh regenerates only cases that still carry it, so a skeleton the V&V team expanded is never overwritten.
`cases_updated_at` is the last refresh; `scenarios_source` is `phase5` or `ticket_edit`, the latter when phase 7
picked up a hand edit of the approved block. A refresh happens when `scenarios_written_at` is later than the
cases, and an approval only counts when it postdates `scenarios_written_at`.

**Jira labels are the source of truth, not this file.** `state` mirrors the ticket's pipeline label; when
they disagree the next run follows Jira and repairs the file. The log exists to remember *why* a ticket is
where it is (which concerns were raised, when, and who approved) — never to decide where it is.

Lives inside `.buddy-council/`, kept out of git via the repo-local `.git/info/exclude`, like the onboarding log.

## Progress Log Schema Additions

- **`code_mapping`** — `{computed_at: ISO 8601 UTC, git_sha: string|null, files: [{path, role}], flow: string, requirement_locations: [{req_id, files: [{path, lines}]}], notes: [string]}`.
